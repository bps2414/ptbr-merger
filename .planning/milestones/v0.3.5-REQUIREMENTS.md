# Requirements Archive: v0.3.5 Hygiene Baseline

**Archived:** 2026-03-25
**Milestone:** v0.3.5 Hygiene Baseline
**Core Value:** When a 4K movie lacks PT-BR audio, the pipeline must recover a compatible PT-BR source and merge it safely without corrupting or wrongly replacing the original file.

## Delivered Requirements

### Repository Hygiene

- [x] **HYGN-01**: Developer can keep runtime state, logs and cache artifacts out of source control by default
  Outcome: Delivered in Phase 1 via restored `.gitignore`, cache cleanup, and tracked/local boundary enforcement.
- [x] **HYGN-02**: Developer can distinguish tracked source files from local operational files without noisy git status output
  Outcome: Delivered in Phase 1 via boundary audit, quieter `git status`, and README hygiene guidance.
- [x] **HYGN-03**: Developer can keep planning artifacts tracked intentionally while preserving local-only sensitive/runtime files
  Outcome: Delivered in Phase 1 by keeping `.planning/` visible to git while excluding `config.yml`, runtime ledgers, logs, and local tooling artifacts.

## Deferred Requirements

These were part of the initial planning horizon but were explicitly removed from the shipped milestone scope before execution.

### Future Maintainability Work

- **ORCH-01**: Developer can read `src/trigger.py` as smaller orchestration stages with clear responsibility boundaries
- **ORCH-02**: Pipeline behavior for Radarr events, qBittorrent completion and retry replay remains equivalent after refactor
- **ORCH-03**: Existing trigger-focused automated tests still verify orchestration behavior after code movement
- **RANK-01**: Developer can locate Radarr candidate ranking, filtering and fallback rules in dedicated modules instead of one large client file
- **RANK-02**: Candidate scoring behavior for strict, soft and exploratory banks remains covered by automated tests
- **RANK-03**: Developer can change ranking heuristics with less risk of unintended API-client regressions
- **QUAL-01**: Developer can run the project's core validation checks through a single documented automated entrypoint
- **QUAL-02**: Repository can execute test and compile validation automatically in a repeatable local workflow
- **QUAL-03**: Documentation points contributors to the current validation workflow without ambiguity
